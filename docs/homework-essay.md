## 一、项目展示

本项目名为 **Arr0w Voyage（一箭又一箭）**，使用 Python 和 Pygame 开发。玩家需要观察棋盘上箭头之间的阻挡关系，按照正确顺序点击箭头，让所有箭头依次飞出棋盘。

## 二、项目介绍

### 1. 游戏规则

棋盘由若干方格组成，每个箭头格包含上、下、左、右四个方向之一。点击箭头后，程序会沿着箭头方向检查它到棋盘边缘之间的格子：

- 如果路径上没有其他箭头，箭头飞出棋盘并消失；
- 如果路径上存在其他箭头，则本次点击记为一次失误；
- 当棋盘上的箭头全部消失时，本局完成；
- 失误次数耗尽时，本局失败。

普通模式共有三关，失误次数跨关累计，三类道具也在三关内共享。自定义模式则允许玩家自行设置棋盘大小、道具次数和空格比例。

### 2. 界面与视觉风格

我希望界面不要呈现明显的模板化游戏风格，因此没有使用常见的高饱和渐变、厚重阴影和悬浮卡片，而是采用暖色纸张、细线、墨色箭头和少量朱红作为视觉基调。按钮、方格、道具框、提示框和鼠标均使用了统一素材，并通过九宫格缩放避免圆角在拉伸后变形。

### 3. 主要功能

- 三组可解关卡及完整通关流程；
- 上、下、左、右四个方向的阻挡判断；
- 失误次数、红心状态和失败结算；
- 提示、增加失误次数、移出三类道具；
- 箭头飞出、碰撞抖动、提示高亮和 Toast 动画；
- 重新开始与退出确认框；
- 自定义 N×N 棋盘、道具数量和空格比例；
- 自定义棋盘随机生成并保证可解；
- 自动化测试与 SDL 无窗口冒烟测试。

## 三、实现思路

### 1. 棋盘的数据表示

棋盘使用二维列表表示：

```python
Board = list[list[str | None]]
```

其中 `None` 表示空位置，`"UP"`、`"DOWN"`、`"LEFT"`、`"RIGHT"` 表示箭头方向。把纯逻辑与 Pygame 界面分离后，路径判断和关卡测试不需要打开游戏窗口即可运行，降低了调试成本。

### 2. 路径阻挡判断

判断箭头能否飞出的核心逻辑是：从箭头所在位置开始，沿方向逐格向棋盘边缘移动；只要途中遇到任意箭头，就说明被阻挡。

```python
def can_fly_out(board: Board, row: int, col: int) -> bool:
    direction = board[row][col]
    delta_row, delta_col = DIRECTIONS[direction]
    row += delta_row
    col += delta_col

    while 0 <= row < len(board) and 0 <= col < len(board[0]):
        if board[row][col] is not None:
            return False
        row += delta_row
        col += delta_col

    return True
```

这个函数虽然不长，却是整个游戏正确性的基础。四个方向、边缘位置、阻挡与非阻挡情况都围绕它展开，因此我优先为它编写了参数化测试。

### 3. 状态管理与动画

游戏使用枚举维护 `START`、`CUSTOM_CONFIG`、`PLAYING`、`LEVEL_COMPLETE`、`GAME_COMPLETE`、`CUSTOM_COMPLETE` 和 `LOSE` 等状态。点击事件、界面绘制和结算逻辑都根据当前状态分派，避免不同界面的按钮互相误触。

动画状态没有直接混在绘制代码里，而是集中记录飞出箭头、碰撞格、提示格和 Toast 计时。最后一支箭头飞出时，程序不会立刻切换结果页，而是等待飞出动画结束，避免画面突兀。

### 4. 可解棋盘的生成

普通关卡使用反向放置思路构造：每放置一支箭头时，都保证它当前可以飞出。最终按照放置顺序的逆序操作，就一定能够清空棋盘。

自定义模式把这套思路进一步封装成 `generate_random_board()`。函数根据棋盘大小和难度系数计算空位置数量，随机选择箭头位置，并从中心向外安排放置顺序；每次放置前临时测试四个方向是否畅通。这样既保证棋盘随机，又保证生成结果可解。

核心实现代码如下：

```python
def generate_random_board(
    board_size: int,
    difficulty: float,
    *,
    rng: random.Random | None = None,
) -> Board:
    """生成保证可解、且空位置比例接近难度的随机棋盘。"""

    if not MIN_BOARD_SIZE <= board_size <= MAX_BOARD_SIZE:
        raise ValueError("棋盘大小必须在 1 到 10 之间")
    if not 0.0 <= difficulty <= 1.0:
        raise ValueError("难度系数必须在 0 到 1 之间")

    generator = rng or random.Random()
    total_cells = board_size * board_size
    empty_count = min(total_cells - 1, round(total_cells * difficulty))
    arrow_count = total_cells - empty_count

    positions = [
        (row, col)
        for row in range(board_size)
        for col in range(board_size)
    ]
    selected = generator.sample(positions, arrow_count)

    # 越靠近中心的箭头越先放置，这样它到最近边缘的路径仍为空。
    selected.sort(
        key=lambda cell: min(
            cell[0],
            cell[1],
            board_size - 1 - cell[0],
            board_size - 1 - cell[1],
        ),
        reverse=True,
    )

    board: Board = [
        [None for _ in range(board_size)]
        for _ in range(board_size)
    ]

    for row, col in selected:
        clear_directions: list[str] = []

        for direction in DIRECTIONS:
            # 临时放入候选方向，复用 can_fly_out 判断路径是否畅通。
            board[row][col] = direction
            if can_fly_out(board, row, col):
                clear_directions.append(direction)
            board[row][col] = None

        if not clear_directions:
            continue

        board[row][col] = generator.choice(clear_directions)

    return board
```

这里最关键的是排序和“临时放置”。越靠近中心的格子越先处理，因此当它朝最近边缘寻找方向时，路径上的格子尚未放置，候选方向至少有一个是畅通的。按放置顺序的逆序操作，就一定能够逐步清空棋盘。

### 5. 自定义配置界面

自定义模式最初使用圆形旋钮，但实际查看后发现五个旋钮占用空间较大，信息层级不够清楚。后来根据反馈改成五行横向长条滑块：

- 棋盘大小：1 到 10；
- 提示数量：0 到 9；
- 增加失误次数：0 到 9；
- 移出数量：0 到 9；
- 难度系数：0% 到 100%，用于控制空位置比例。

配置页每行由左侧名称、中间滑块和右侧当前值组成，并通过拖动滑块实时更新。调整布局时还专门检查了文字宽度、滑块范围和数值位置，避免左侧留白过多以及右侧数字与滑块重叠。

### AIGC 使用反思

AIGC 最大的帮助不是“一次写对所有代码”，而是提高探索速度和减少重复劳动。它很适合生成模块骨架、样板代码、测试用例和重构方案；但需求是否合理、界面是否耐看、逻辑是否真正满足约束，仍然需要人来判断。

例如，圆形滑块在功能上完全可用，但实际页面中信息拥挤，最终还是要根据视觉效果改成五行长条。自定义棋盘生成器也曾隐藏了一个边界错误，只有主动进行批量可解性验证后才暴露出来。这说明 AI 输出必须经过运行、测试和人工审查，不能把“代码能跑”等同于“功能正确”。

## 七、心得体会

这次作业让我最直观地感受到，软件工程和“写出一段能运行的代码”并不是一回事。

第一，需求需要被转化成可验证的条件。例如“生成随机棋盘”听起来很简单，但如果只追求随机，可能生成无解棋盘。因此我把要求进一步解释为“随机、尺寸正确、空格比例正确、保证可解”，再为每个条件写测试。只有这样才能确认功能真的完成。

第二，AI 适合加速，但不适合代替判断。AI 能很快生成界面、逻辑和测试，但它不一定知道课程要求、真实视觉质量和隐藏边界。圆形改成长条、滑块内容左移、说明文字靠近滑块，这些反馈都来自实际观察；随机生成器的空格错误则来自主动验证。人的任务不是简单接受代码，而是定义标准、发现问题并决定修改方向。

第三，测试是重构的底气。项目从最初的单个 `game.py` 拆出 `logic.py`、`tools.py`、`animations.py`、`audio.py`、`custom_mode.py` 后，之所以敢继续修改，是因为每一步都有自动化测试回归。测试不仅用于提交，也帮助我理解模块之间的依赖关系。

当然，项目仍有不足。测试报告中的历史数据和最终测试数量还需要进一步同步；自定义棋盘的视觉多样性还可以继续优化；真实窗口下的长时间试玩和不同分辨率适配也仍需要补充。今后如果继续完善，我希望加入截图回归测试、更多随机种子验证和更完整的用户操作测试。

总体来说，这次作业让我完成了从需求分析、界面设计、逻辑实现、AIGC 协作到测试和文档整理的完整过程。相比最后得到的一个小游戏，我更重视的是学会了如何把模糊想法拆成可执行、可检查和可修改的工程任务。
